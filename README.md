# squarespace-steps

[![Test](https://github.com/webship/squarespace-steps/actions/workflows/test.yml/badge.svg)](https://github.com/webship/squarespace-steps/actions/workflows/test.yml)

A [webship-js](https://github.com/webship/webship-js) Cucumber/Playwright test project for [Squarespace](https://www.squarespace.com/) sites: navigation and the mobile menu, hero, footer, forms and the newsletter block, shop and cart, blog, gallery, site search, the announcement bar, the cookie banner, and the facts a page reports about itself.

This repository contains:

- **Squarespace step definitions** in `tests/step-definitions/`, loaded through `squarespace.steps.js` alongside webship-js's own built-in steps.
- **A self-test harness**: a static demo site (`demo-site/`) that carries the markup Squarespace really renders, and a set of `.feature` files (`tests/features/`) that exercise the steps in CI.
- **Read-only real-site features** (`tests/features/real-sites/`) that run the same steps against public Squarespace template demos. They are not part of CI; see "Checks on real sites".

## What the steps match

The selectors were read from the markup of public Squarespace template demos, not written from memory. Squarespace 7.1 is the first target. The 7.0 steps cover the Brine family (class names that start with `Header-`, `Footer-`, `Mobile-`); other 7.0 template families use different class names and are not covered. Each step's JSDoc names the classes it uses, and [docs/selector-evidence.md](docs/selector-evidence.md) lists the pages they were read from, what could not be observed on a live site, and the raw counts. `npm run probe -- <url>` counts the pack's selectors on any page.

Two facts about the real markup shape the steps:

- Squarespace 7.1 renders the header twice, a desktop copy and a mobile copy, and hides one of them. The steps act on and assert the copy a person can see.
- Labels are compared after collapsing whitespace, and case sensitive, as the page source writes them. A template that styles its menu in capitals with CSS keeps the source text; a template that writes "BLOG" in the page needs "BLOG" in the feature.

Squarespace is a hosted product with no self-hostable distribution, so CI cannot start a real Squarespace site. `demo-site/` is generated by `npm run demo:build` (`scripts/build-demo-site.js`) from the markup of the real templates, so the suite has a stable, versioned target. The steps cover the public site only; nothing here needs an account.

To point the suite at a real site, set `LAUNCH_URL` to that site's URL when running `npm test`.

## Checks on real sites

`npm run test:real-sites` runs the `@real-site` features against five public template demos (Bailard, Loam, Soony and Hester on 7.1; Brine on 7.0). They never send anything to the site: they do not submit the form block, add to a cart or sign up. The sites are third-party demos and can change; a failure there means the template changed or a selector drifted, so check the page before changing a step. To run one site: `npm run test:real-sites -- @bailard`.

## From nothing to a green run

What the machine needs: git and Node.js 20 or later with npm. No container: the
demo site is a folder of static pages.

**1. The site.** The demo site of this repository: static pages generated from
the markup of real Squarespace 7.1 templates (the header twice, folders and the
mobile menu, a hero, the form and newsletter blocks, a shop with product pages
and a cart count, a blog, a gallery, the search page, the footer and the
`Static.SQUARESPACE_CONTEXT` a page reports). Serve it and leave the server
running in its own terminal:

```bash
git clone https://github.com/webship/squarespace-steps.git
cd squarespace-steps
npx http-server demo-site -p 8080 -s
```

The site answers at `http://localhost:8080`.

**2. A test project**, in another terminal:

```bash
mkdir squarespace-tests && cd squarespace-tests
npm init -y
npm install --save-dev webship-js @webship-js/squarespace-steps
npx init-webship-js
```

`npx init-webship-js` writes `cucumber.js`, `playwright.config.ts`, the
`tests/` folders with a first feature and the `npm test` scripts, and installs
Chromium. npm usually runs it already when it installs webship-js; a second run
changes nothing.

**3. `cucumber.js`.** Replace the file with the wiring of the pack: the step
files of webship-js and the entry file of the pack, and the address of the
site. The suite needs no account (see [Test users](#test-users)).

```javascript
module.exports = {
  default: {
    requireModule: ['tsx/cjs'],
    require: [
      'node_modules/webship-js/tests/step-definitions/**/*.js',
      'node_modules/@webship-js/squarespace-steps/tests/step-definitions/squarespace.steps.js',
      'tests/step-definitions/**/*.js',
    ],
    paths: ['tests/features/**/*.feature'],
    format: ['@cucumber/pretty-formatter', 'json:tests/reports/cucumber_report.json'],
    worldParameters: {
      launchUrl: process.env.LAUNCH_URL || 'http://localhost:8080',
      // The waits webship-js adds around each page, scenario and step (milliseconds).
      minWaitTime: { page: 3000, before_scenario: 0, after_scenario: 0, before_step: 0, after_step: 0 },
    },
  },
};
```

**4. A first feature**, `tests/features/first-run.feature`:

```gherkin
Feature: First run
  Scenario: The home page reports its facts and its hero
    Given I am on the homepage
    Then the site should use version "7.1"
    And the site title should be "Demo Studio"
    And the hero title should be "Handmade goods, honestly sourced."
    And "Home" should be the current navigation item

  Scenario: The shop lists its products
    Given I am on the "/shop.html" page
    Then the shop should list 3 products
    And the shop should list the product "Ceramic Mug"
```

**5. Run it.**

```bash
npm test
```

A green first run prints every step, then the summary (the starter feature of
`npx init-webship-js` and the two scenarios above, passed) and the HTML report
it wrote:

```
3 scenarios (3 passed)
10 steps (10 passed)
0m01.907s (executing steps: 0m01.874s)
[webship-js] HTML report → …/squarespace-tests/tests/reports/cucumber_report.html
```

From there, copy the features of [`tests/features/`](tests/features/) (they
also ship in the package, under
`node_modules/@webship-js/squarespace-steps/tests/features/`): together they use
every step of the pack, against the pages of the demo site.
`banners.feature` switches the announcement bar and the cookie banner on in the
test browser with the two test aids of
`tests/step-definitions/support/squarespace-site-settings.steps.js` (they ship
too; add that file to `require` to use them): the demo, like the public
template demos, has both off.

### What the suite tests

The features of this repository run every step of the pack against the demo
site, and CI serves it and runs them on every change: the header navigation
(its items, the current item, folders) and the mobile menu, the hero title and
button, the footer (its links, its copyright line), the facts a page reports
(version, site title, language), the form block (the errors of an empty or a
partly filled form, the confirmation) and the newsletter block (its browser-side
errors, the confirmation), the shop (the product list, a product page, its
price, the quantity, adding to the cart from the list and from the product page,
the cart count across pages), the blog (the list, a post, its author and date),
the gallery, the search page (results and no results), and the announcement bar
and the cookie banner (their text, link, closing, accepting and declining). The
assertions run in their positive and in their negative form, but two: a site has
one footer on every page, with its copyright line, so the negative of
`the site footer should be visible` and of
`the footer should show a copyright notice` cannot be true on the demo.

Not tested: what Squarespace itself does on the server. The demo stands in for
it: the form block's submission and its stored entries, the cart page and the
checkout, payments, member areas, scheduling and the editor. The demo is
generated from the markup of public template demos, and the templates can
change: the read-only features of `tests/features/real-sites/` and
`npm run probe` check the selectors on the public demos, outside CI. A run
leaves nothing: the site is static and the cart lives in the browser.

## Setup

```bash
npm install
npx playwright install chromium
```

## Running tests

```bash
npm run demo:serve &          # serves demo-site/ on http://localhost:8080
npm test                      # runs tests/features/*.feature against it
npm run test:examples         # checks the JSDoc examples and the feature steps against the step regexes
```

CI (`.github/workflows/test.yml`) runs the same flow on every push and pull request.

## Test users

None. The steps cover the public site only, and the suite tests the demo site
of this repository (`demo-site/`), which has no sign-in: `cucumber.js` lists no
accounts (its `worldParameters` has no `users`) and no scenario signs in. The
JSON of the accounts is empty:

```json
{}
```

Every Then step takes `should` or `should not`, every action takes `I`, `we` or no pronoun, and every failure is a friendly message with a hint (no assertion or Playwright stack). Each assertion polls its condition for the `minWaitTime.page` budget (at least 10 s) instead of reading the page once, and every click this pack performs settles the page before the next step.


Forms: a field is found by its label as a person reads it ("Email", not "Email (required)"); a "Name" field is two fields, "First Name" and "Last Name". The form block (`.form-wrapper`) validates on the server: "I submit the form" posts the form to Squarespace, which shows the errors or stores the submission, so use it only on a site you own. The newsletter block (`.newsletter-form`) stops an empty or wrong address in the browser and sends nothing. The confirmation of the form block (`.sqs-form-block-submission-html`) was not observed on a live site, because that needs a real submission; the newsletter confirmation (`.form-submission-text`) and the error markup were read from Squarespace's own scripts and pages.

Shop: the product list shows titles and prices and links to the product page; the "Add to cart" button and the quantity field are on the product page, so "I add the product ... to the cart" opens the product first when it is called on the list. The cart count is the visible `.sqs-cart-quantity` of the header (a hidden or missing count is 0). The add steps create a cart on the site and were run only against `demo-site/`; the real-site features read the list, the product page, the quantity field and the cart link.

Blog, gallery and search: a post is found by its exact title; the author and the date are compared as the page writes them (the date format is a site setting). The gallery count covers gallery grids and reels; the lightbox was not observed open on any public demo and is not covered. "I search the site for" opens `/search` when the page has no search field, types the words and presses Enter.

Announcement bar and cookie banner: both are off until the site owner switches them on, and none of the public template demos has either. The steps use the markup that Squarespace's own scripts draw (`.sqs-announcement-bar`, `section.gdpr-cookie-banner`). To prove them on a real template, the `@real-site` features use two test-support steps (`tests/step-definitions/support/`, shipped beside the steps but loaded only when a project adds that file to `require`) that switch the settings on in the test browser by rewriting the page's `Static.SQUARESPACE_CONTEXT`; nothing on the site changes. The cookie banner shows only to the visitors the site's cookie settings select, often only in the EU, so a test from elsewhere may not see it.

Two things to know:

- The hero title is the first level-one heading of the page content, outside the header, the footer and list items such as blog posts. A page with no such heading has no hero title.
- The reference features assert the demo site's own copy, counts and paths ("Our story", `/shop.html`, ...), so swap those values for your site's content when you copy a feature.

Every step's regex and five Gherkin examples are in the JSDoc block above it; `npm run test:examples` checks that each example matches its own step (and no webship-js core step) and that every feature step is defined exactly once. CI runs it before the suite.

## Lanes, subsets and settings

- `npx cucumber-js tests/features/home.feature` runs one feature and `npx cucumber-js tests/features/home.feature:<line>` one scenario (the line of its `Scenario:`; the paths of `cucumber.js` are left out when the command line names any, and `npm run test:paths` checks it); `FEATURES=tests/features/a.feature,tests/features/b.feature npm test` runs a subset of the feature files too; `CUCUMBER_TAGS=@critical npm test` runs a tag lane (the default run leaves `@wip` out).
- `cucumber.js` carries the `video` block (`WEBSHIP_VIDEO=on-failure` records the browser) and the `javascript` block (`WEBSHIP_JS_ERROR_MODE=fail` fails a scenario on a JavaScript error; `@js-off` silences one scenario) that webship-js reads.
- The step timeout is webship-js's own (45 seconds, set when it loads); `WEBSHIP_STEP_TIMEOUT=<milliseconds>` changes it, a `timeout` key in `cucumber.js` does not.
