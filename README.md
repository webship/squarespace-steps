# squarespace-steps

[![Test](https://github.com/webship/squarespace-steps/actions/workflows/test.yml/badge.svg)](https://github.com/webship/squarespace-steps/actions/workflows/test.yml)

A [webship-js](https://github.com/webship/webship-js) Cucumber/Playwright test project for [Squarespace](https://www.squarespace.com/) sites: navigation and the mobile menu, hero, footer, forms, shop and cart, blog, and the facts a page reports about itself.

This repository contains:

- **Squarespace step definitions** in `tests/step-definitions/`, loaded through `squarespace.steps.js` alongside webship-js's own built-in steps.
- **A self-test harness**: a static demo site (`demo-site/`) that carries the markup Squarespace really renders, and a set of `.feature` files (`tests/features/`) that exercise the steps in CI.
- **Read-only real-site features** (`tests/features/real-sites/`) that run the same steps against public Squarespace template demos. They are not part of CI; see "Checks on real sites".

## What the steps match

The selectors were read from the markup of public Squarespace template demos, not written from memory. Squarespace 7.1 is the first target. The 7.0 steps cover the Brine family (class names that start with `Header-`, `Footer-`, `Mobile-`); other 7.0 template families use different class names and are not covered. Each step's JSDoc names the classes it uses.

Two facts about the real markup shape the steps:

- Squarespace 7.1 renders the header twice, a desktop copy and a mobile copy, and hides one of them. The steps act on and assert the copy a person can see.
- Labels are compared after collapsing whitespace, and case sensitive, as the page source writes them. A template that styles its menu in capitals with CSS keeps the source text; a template that writes "BLOG" in the page needs "BLOG" in the feature.

Squarespace is a hosted product with no self-hostable distribution, so CI cannot start a real Squarespace site. `demo-site/` is generated by `npm run demo:build` (`scripts/build-demo-site.js`) from the markup of the real templates, so the suite has a stable, versioned target. The steps cover the public site only; nothing here needs an account.

To point the suite at a real site, set `LAUNCH_URL` to that site's URL when running `npm test`.

## Checks on real sites

`npm run test:real-sites` runs the `@real-site` features against four public template demos (Bailard, Loam and Soony on 7.1; Brine on 7.0). The steps they use only read the page: they do not submit forms, add to a cart or sign up. The sites are third-party demos and can change; a failure there means the template changed or a selector drifted, so check the page before changing a step. To run one site: `npm run test:real-sites -- @bailard`.

| Check | Bailard 7.1 | Loam 7.1 | Soony 7.1 | Brine 7.0 |
| --- | --- | --- | --- | --- |
| Header navigation, current item | yes | yes | no page links in the header | yes |
| Navigation folder | yes | | | |
| Mobile menu open and close | yes | | | yes |
| Hero title and button | yes | | | |
| Footer | yes | yes | yes | yes |
| Site facts (`Static.SQUARESPACE_CONTEXT`) | yes | yes | yes | yes |

## Setup

```bash
npm install
npx playwright install chromium
```

## Running tests

```bash
npm run demo:serve &          # serves demo-site/ on http://localhost:8080
npm test                      # runs tests/features/**/*.feature against it
```

CI (`.github/workflows/test.yml`) runs the same flow on every push and pull request.

## Step definitions

The steps live in `tests/step-definitions/` and are loaded through `squarespace.steps.js`. To use them in another webship-js project, install `@webship-js/squarespace-steps` and add `node_modules/@webship-js/squarespace-steps/tests/step-definitions/squarespace.steps.js` to that project's `require` list in `cucumber.js`.

| Step | Type |
| --- | --- |
| `the (site\|main )navigation should( not) contain "<label>"` | Then |
| `"<label>" should( not) be the current navigation item` | Then |
| `the (desktop\|main\|site) navigation should( not) be visible` | Then |
| `the mobile (navigation\|menu) toggle( button) should( not) be visible` | Then |
| `I open the mobile (navigation )menu` | When |
| `I close the mobile (navigation )menu` | When |
| `the mobile (navigation )menu should( not) be open` | Then |
| `the mobile (navigation )menu should( not) contain "<label>"` | Then |
| `I open the "<folder>" navigation folder` | When |
| `the "<folder>" navigation folder should( not) contain "<label>"` | Then |
| `the hero title should( not) be "<title>"` | Then |
| `the hero (call-to-action button\|CTA) should( not) link to "<href>"` | Then |
| `the (site )footer should( not) be visible` / `I should( not) see the footer` | Then |
| `the (site )footer should( not) show\|display a copyright( notice)` | Then |
| `the footer navigation should( not) contain "<label>"` | Then |
| `the site should( not) use Squarespace 7.1\|7.0` | Then |
| `the site title should( not) be "<title>"` | Then |
| `the site language should( not) be "<language>"` | Then |
| `I fill in the (Squarespace )form field "<label>" with "<value>"` | When |
| `I submit the (Squarespace )form` | When |
| `the (Squarespace )form should( not) show the submitted confirmation( message)` / `I should( not) see the form submitted confirmation` | Then |
| `the shop should list <n> product(s)` | Then |
| `I add the product "<title>" to the cart` | When |
| `the cart should contain <n> item(s)` | Then |
| `the blog should list <n> post(s)` | Then |
| `the blog post "<title>" should( not) be visible` | Then |

The product word is optional ("the Squarespace form" and "the form" both match). Every Then step takes `should` or `should not`, every action takes `I`, `we` or no pronoun, and every failure is a friendly message with a hint (no assertion or Playwright stack). Each assertion polls its condition for the `minWaitTime.page` budget (at least 10 s) instead of reading the page once, and every click this pack performs settles the page before the next step.

Two things to know:

- The hero title is the first level-one heading of the page content, outside the header, the footer and list items such as blog posts. A page with no such heading has no hero title.
- The reference features assert the demo site's own copy, counts and paths ("Our story", `/shop.html`, ...), so swap those values for your site's content when you copy a feature.

Every step's regex and five Gherkin examples are in the JSDoc block above it; `npm run test:examples` checks that each example matches its own step (and no webship-js core step) and that every feature step is defined exactly once. CI runs it before the suite.

### Lanes, subsets and the settings webship-js reads

- `FEATURES=tests/features/a.feature,tests/features/b.feature npm test` runs a subset of the feature files; `CUCUMBER_TAGS=@critical npm test` runs a tag lane (the default run leaves `@wip` out).
- `cucumber.js` carries the `video` block (`WEBSHIP_VIDEO=on-failure` records the browser) and the `javascript` block (`WEBSHIP_JS_ERROR_MODE=fail` fails a scenario on a JavaScript error; `@js-off` silences one scenario) that webship-js reads.
- The step timeout is webship-js's own (45 seconds, set when it loads); `WEBSHIP_STEP_TIMEOUT=<milliseconds>` changes it, a `timeout` key in `cucumber.js` does not.
